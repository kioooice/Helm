# 验收约定

本文件定义评判依据，不表示功能已经实现。阶段边界见 [PLAN.md](../PLAN.md)，开发分工见 [AGENTS.md](../AGENTS.md)。

## 一条发现应当能回答什么

| 内容 | 最小要求 |
| --- | --- |
| 发现 | 具体说清观察到了什么，避免只有笼统建议 |
| 依据 | 稳定来源 ID、时间或片段定位，能在授权范围内核对 |
| 覆盖 | 使用了哪些记录，已知遗漏/截断，未知部分明确为未知 |
| 推理 | 区分直接观察、解释假设与待确认问题；说明关键不确定性 |
| 比较 | 如声称发生变化，给出可比时段和依据；没有就不比较 |
| 用户关系 | 只有用户确认过的目标才能标成目标；模型推断单独标注 |
| 纠正 | 记录用户补充或争议，后续结果说明是否以及如何采用 |

这些是语义要求，不强制当前立即创建数据库表或 JSON schema。样本阶段用简短文本即可。允许“证据不足，暂不提出发现”；证据失效后不得继续显示成可核查结论。

## 必须覆盖的反例

- 零散窗口切换：不能直接断言分心或计算一天的注意力比例。
- 只有当日片段：不能断言比平时变好/变差。
- 一段阅读记录：不能断言没有产出或没有价值。
- 用户曾提过某方向：不能永久当作已确认目标，忽略后续变化。
- 源记录缺失或过期：明确不可核查，不生成虚构引用。
- 用户纠正模型：保留纠正范围，避免下一轮原样重复被否定解释。
- 没有有意义的新发现：允许简短无发现结果，不凑条数。

代码验收可用合成数据检验引用有效性、覆盖元数据、取消请求、纠正读取等确定行为。推理质量需要阅读实际输出；另一模型的评分只作辅助。

## 分开验收三个问题

1. **技术事实是否成立**：规划助手检查源码、请求、数据与验证记录。测试命令、环境和提交必须对应；未运行就标未验。
2. **推理是否站得住**：规划助手逐条核对来源、比较、推断和反例，不能只看输出流畅程度。
3. **对本人是否有意义**：用户判断是否带来新认识、帮助决定或值得再次看。不要由模型代替用户打“有用”分。

用户反馈可以很轻：哪些内容已知、哪条有用、哪里理解错了；需要进一步判断时再追问。不要求每天填写量表。无反馈表示未知，既不能算成功，也不能算失败。

## 阶段交接模板

- 任务 ID / 工作基线 / 结果提交：
- 本次完成与范围外内容：
- 验收条目及对应证据：
- 实际验证命令、环境和结果：
- 实际输出与反例结果（仅授权材料，公开仓库使用合成或适当脱敏示例）：
- 未验证项、已知问题及影响：
- 用户价值反馈：已获得 / 尚未获得；事实记录：
- 规划助手结论：待验收 / 通过 / 有条件通过 / 返工 / 暂停：
- 条件或返工项、允许继续的范围：

执行模型提交时结论默认为“待验收”。规划助手复核后填写结论；通过一个技术任务不自动通过下一产品阶段。
